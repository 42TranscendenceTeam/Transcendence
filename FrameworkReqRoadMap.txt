Framework Migration Roadmap — Custom CSS + Tailwind (Layout/Spacing Only)
======================================================================

Status: Tailwind CSS is installed and configured (@tailwind directives in
01-variables.css, tailwind.config.js and postcss.config.js exist) but zero
Tailwind utility classes are used in JSX. All 15 custom CSS files interleave
layout/spacing rules with visual/theme rules within the same class definitions.

Goal: Use Tailwind utility classes for layout/spacing only. Keep all visual/
theme properties (colors, gradients, glows, borders, shadows, fonts,
transitions) in the existing custom CSS files. No Bootstrap.

Rationale
---------
- Tailwind is already installed — zero setup cost
- Incremental per-component migration — no breaking changes
- Custom dark neon theme is preserved entirely in CSS variables
- No dependency conflicts (Bootstrap classes would clash with existing .btn,
  .card, .modal classes)
- Layout/spacing (flex, grid, gap, padding, margin, width, height) is the
  boilerplate part of CSS — Tailwind handles it more concisely in JSX

Principle: Split by Concern
----------------------------
MOVE TO TAILWIND UTILITIES (in JSX className):
  flex / grid / gap / padding / margin / width / height / min-height /
  max-height / max-width / position / top / left / right / bottom /
  overflow / display / align-items / justify-content / flex-direction /
  flex-wrap

KEEP IN CUSTOM CSS (unchanged, per class):
  color / background / background-image / border-color / border-radius /
  box-shadow / backdrop-filter / font-family / font-size / font-weight /
  letter-spacing / line-height / transition / filter / gradient / opacity /
  z-index / cursor / text-decoration / outline

Both can coexist in the same element: <div className="friend-chat-container
  flex-1 flex flex-col overflow-hidden min-h-0"> where the class
  friend-chat-container still provides bg-card, border, border-radius from
  the CSS file.

Phase 1 — Configure Tailwind Palette (one-time, ~15 min)
----------------------------------------------------------
Add your custom color variables to theme.extend in tailwind.config.js.
Now 'bg-card', 'text-accent', 'border-border', 'shadow-btn-glow' etc. work
as Tailwind utilities.

Example tailwind.config.js:
  export default {
    content: ['./index.html', './src/**/*.{js,ts,jsx,tsx}'],
    theme: {
      extend: {
        colors: {
          card: '#141d2f',
          'card-hover': '#171b2b',
          primary: '#060815',
          'text-primary': '#f8fafc',
          'text-secondary': '#a1a1b5',
          accent: '#8b5cf6',
          'accent-hover': '#6366f1',
          border: '#272b3f',
          'border-light': '#383d5a',
          success: '#22c55e',
          error: '#f43f5e',
          'neon-purple': '#a07dda',
          'neon-blue': '#4f8cff',
          'neon-pink': '#d946ef',
        },
        boxShadow: {
          'btn-glow':
            'inset 0 0 0 1px rgba(255,255,255,0.04), 0 0 18px rgba(139,92,246,0.18)',
          'btn-glow-hover':
            '0 0 24px rgba(139,92,246,0.28), 0 0 6px rgba(79,140,255,0.18)',
        },
      },
    },
    plugins: [],
  }

Phase 2 — Per-Component Migration (one component per session)
---------------------------------------------------------------
Per component:
  1. Read the .tsx file and its CSS file
  2. For each custom CSS class used in the JSX:
     a. Identify which rules are layout/spacing (Tailwind candidates)
     b. Identify which rules are visual/theme (keep in CSS)
  3. Add Tailwind utility classes to the JSX className
  4. Optionally remove the layout/spacing rules from the CSS class
     definition (leaving only visual rules). Or leave them — Tailwind
     utilities in className will override them when both target the same
     property due to Tailwind's higher specificity.

Example — FriendChat friend-chat-container:
  Current CSS:
    .friend-chat-container {
      flex: 1;                // layout → Tailwind: flex-1
      display: flex;           // layout → Tailwind: flex
      flex-direction: column;  // layout → Tailwind: flex-col
      background: var(--bg-card);   // visual → keep in CSS
      border: 1px solid var(--border); // visual → keep in CSS
      border-radius: 1rem;          // visual → keep in CSS
      overflow: hidden;        // layout → Tailwind: overflow-hidden
      min-height: 0;           // layout → Tailwind: min-h-0
    }

  Result JSX:
    <div className="friend-chat-container flex-1 flex flex-col overflow-hidden min-h-0">

  Result CSS (after cleanup):
    .friend-chat-container {
      background: var(--bg-card);
      border: 1px solid var(--border);
      border-radius: 1rem;
    }

Phase 3 — Optional CSS Pruning (when a file is fully migrated)
---------------------------------------------------------------
Once all classes in a CSS file have no layout rules remaining, you may:
  - Keep the file as a visual-only companion (cleaner separation)
  - Or delete the file and use Tailwind utility equivalents via the
    palette configured in Phase 1 (e.g. bg-card instead of the class)

The second option is purely optional — the visual-only CSS files are
perfectly maintainable as-is.

Migration Order (suggested)
----------------------------
Pilot component first, then increasing complexity:
  1. FriendChat.tsx + 08-chat.css       (self-contained, moderate)
  2. Teams / TeamDetail.tsx + 07*.css    (medium)
  3. Auth pages + 04-auth.css            (medium)
  4. Profile pages + 06*.css             (medium)
  5. Modals + 09-modals.css              (easy, short file)
  6. Feed + 05*.css                      (largest surface area, save for last)

What NOT to Do
---------------
- Do NOT install Bootstrap (clashing class names, new dependency, extra config)
- Do NOT rewrite all files at once (breaks the incremental benefit)
- Do NOT delete custom CSS files prematurely (component will lose visuals)
- Do NOT try to replace complex visual effects with Tailwind (gradients,
  glows, backdrop-filter are harder to express in Tailwind than in CSS)

Class Ordering Convention (mandatory for all migrated components)
------------------------------------------------------------------
Tailwind utility classes must follow this order within className:

  1. Display/Layout    (flex, grid, block, inline-flex)
  2. Sizing            (w-full, h-*, flex-1, min-w-*, max-w-*, min-h-*)
  3. Positioning       (relative, absolute, fixed, sticky)
  4. Overflow          (overflow-*, etc.)
  5. Spacing           (p-*, m-*, gap-*, px-*, py-*, pt-*, pb-*, pl-*, pr-*)
  6. Alignment         (items-center, items-stretch, justify-*, justify-self-*)
  7. Typography        (text-*, font-*, tracking-*, leading-*)
  8. Colors            (text-*, bg-*, border-*)
  9. Effects           (rounded-*, shadow-*, opacity-*, backdrop-*, cursor-*)

  CSS custom classes (.btn, .card, .auth-*, .feed-*, etc.) always come FIRST
  before any Tailwind utilities.

  Example CORRECT:
    className="auth-divider flex items-center gap-4 text-center"
    className="mb-2 text-text-secondary"

  Example INCORRECT:
    className="flex text-center auth-divider items-center gap-4"
    className="text-text-secondary mb-2"

Key Benefits of This Approach
------------------------------
- No breaking changes at any commit
- Can stop at any time with a working project
- Custom visual identity (neon/dark theme) is untouched
- Layout code becomes more concise (one className string vs. CSS file)
- All team members can adopt at their own pace per component
